# ADR-006: 明确不做的优化（Out-of-Scope）及其判定依据

## Status

Accepted (2026-08-23)

## Background

高 QPS 场景有一批「看起来该做」的常规优化。本 ADR 逐条给出**不做的量化依据**，
避免后续有人凭直觉重新提出，也避免实施方把精力花在收益不成比例的地方。

判定原则：**收益必须可量化，且与风险/复杂度成比例。**

## Decision — 不做的事

### 1. 不做本地限流缓存/令牌桶做主判定

**理由：这是 P0-1 的根因，不是优化。**
N 个实例各持独立桶 → 实际配额 = limit × N，「保护下游总量」完全落空
（`local.go:8-15` 已明确记录）。
任何形式的「本地先判、Redis 后补」都会放宽判定。
**违反「不得以正确性换性能」硬约束，直接否决。**

### 2. 不做 Redis Pipeline 批量合并多请求

设想：把多个并发请求的 `batch_check` 攒成一个 pipeline 发送。

**否决理由（双重）：**
- **正确性**：攒批需要等待窗口，期间请求的判定顺序变得不确定。
  两阶段求值的原子性建立在「单请求单脚本」之上，
  攒批会引入跨请求的中间态 —— 正是 P0-5 修复的反面。
- **收益不成立**：实测 Redis 已 100% 跑满单核（真实 batch_check 约 31k QPS 饱和），
  瓶颈是 Redis 单线程 CPU 而非网络往返次数。
  pipeline 减少的是 syscall 与 RTT，但脚本执行成本不变，
  在已饱和的情况下吞吐几乎不动。
  真正有效的是减少**每请求的往返数**（ADR-003），而非合并**跨请求**的往返。

### 3. 不引入 Redis Cluster / 读写分离

- 限流计数器天然是写操作，读写分离对写路径零收益。
- Cluster 会让多 Key 的 Lua 脚本受 hash slot 约束
  —— `batch_check` 的 KEYS 跨多个维度（global/biz/ip/token），
  不同 slot 会直接导致 `CROSSSLOT` 错误，必须重构 Key 设计或加 hash tag。
  这是架构级改动，远超「增量优化」范围。
- MVP 阶段单 Redis 约 31k QPS（真实 4 规则脚本实测）的天花板对多数场景够用。
  真需要突破时再上，且届时应先评估「按 biz 分片多个独立 Redis」这一
  复杂度低得多的方案。

### 4. 不做 `net/http` 替换为 fasthttp / 第三方框架

- 项目定位是「零 Web 框架」，README 与既有设计明确。
- 实测瓶颈在 Redis（单核跑满，约 31k QPS 饱和）与准入路径 CPU，不在 HTTP 解析。
- fasthttp 不支持 HTTP/2，且其 `RequestCtx` 复用模型与 SSE 长连接
  配合复杂，`http.Flusher` 语义需重写。
  **风险巨大、收益未证实、且会破坏 SSE 零缓冲的现有保障。**

### 5. 不做 `HashToken` 的缓存或替换为更快哈希

实测 `HashToken` = 138.7 ns/op，176 B，3 allocs
（SHA256 + hex，每请求一次，`handler.go:129`）。

- 占准入路径 1785ns 的 7.8%，绝对值小。
- 换非加密哈希（xxhash 等）会降低抗碰撞性
  —— Token 哈希碰撞意味着**两个不同用户共享配额**，是安全问题（Advisory-7
  明确要求 96bit 抗碰撞长度）。
- 加缓存需要以原始 Token 为 key，等于在内存中持有明文 Token 映射，
  与「避免明文 Token 落入 Redis Key 与日志」的设计意图冲突。

**结论：收益 7.8% 而风险涉及安全，不成比例。**

### 6. 不对 `localFallback.quotas` 做原子短路

与 ADR-002 的 `blocks` 短路形成对比：

- `quotas` 仅在 Redis 故障降级期间被调用（`limiter.go:313`、`ledger.go:38`），
  属冷路径，稳态零调用。
- `blocks` 短路安全是因为「最坏退化为走 Redis 权威判定」；
  而 `quotas` 在降级期间**就是唯一的判定依据**，
  其正确性依赖精确计数，短路会导致本地配额判定失准 → 放宽限流。

**同一手法在一处安全、在另一处危险，这个区分必须保留在文档里。**

### 7. 不做 SSE 写入侧缓冲/攒帧

任何形式的下游写缓冲都会破坏零缓冲语义（`stream.go:12-14` 硬约束）。
ADR-005 池化的是**上游读缓冲**，两者不可混淆。
实施时若发现首字节延迟上升，即为触碰此红线，必须回退。

### 8. 不做 `obs/metrics.go` 的锁优化

现状每次指标写入走一次 `RWMutex` 读锁 + map 查找
（`metrics.go:39-53`）。理论上可优化为分片或预解析标签。

**不做的理由**：`/metrics` 实测 8043 B / 113 行 / 3.9-5.1ms 响应
（含 HTTP 往返与 curl 启动开销，实际序列化远低于此）。
指标写入在请求路径上约 2-4 次，相对 Redis 往返（p50 2.4ms @256并发）
可忽略。**在拿到 CPU profile 证明它是热点之前，这属于无依据的优化。**

顺带回答 OPEN-DECISIONS 第 3 项（看板轮询 vs SSE 推送）：
`/metrics` 单次响应 8043 B、耗时约 4ms，**5s 轮询完全可行**，
无需引入推送端点扩大攻击面。**建议按轮询实施并关闭该未决项。**

### 9. 不做配置读取路径优化

`store.Rules(biz)`（`store.go:117-127`）每请求调用，
内部有 `append` 分配（合并全局规则 + biz 规则）。

看似可预计算合并结果。**但收益需先测量**：
当前无该路径的基准数据，`atomic.Pointer` 读本身是无锁的，
分配量取决于规则数（demo 为 4 条）。
**登记为「需 POC 验证」而非直接实施** —— 避免在未测量的地方做优化，
这正是 gc-guide 警告的反模式。

## Consequences

**正面**

- 实施方不会把精力花在 5 项伪优化上，聚焦 ADR-001/002/003/004/005。
- 每条否决都有量化依据或明确的正确性论证，可追溯、可复审。
- 顺带关闭 OPEN-DECISIONS 一项未决问题。

**负面**

- 第 2、3 项的否决基于「单 Redis 约 31k QPS（真实规则集）够用」这一前提。
  若业务目标超过该量级，需重新评估分片方案，本 ADR 需相应修订。
- 第 9 项留作未决，需后续 profile 数据支撑。
