# ADR-007: 修正 go-redis 已知漏洞暴露面（DisableIndentity）

## Status

Accepted (2026-08-23)

## Background

项目当前依赖 `github.com/redis/go-redis/v9 v9.5.3`（`go.mod`）。
该版本存在两个应处理的问题，均在本次官方文档核查中发现，
与性能优化无直接关系但会影响连接建立的正确性：

**一、版本已被撤回（retracted）**

pkg.go.dev 上 v9.5.3 标注：
"This version was accidentally released. Please use version 9.6.0 instead."

**二、GO-2025-3540 / CVE-2025-29923**

`CLIENT SETINFO` 在建连超时时可能导致**响应乱序**。
影响范围 `>= 9.5.1`，修复版本为 9.5.5 / 9.6.3 / 9.7.3。

触发条件（三者叠加）：
1. 客户端配置了传输身份信息（默认开启）
2. 网络连通性问题
3. **客户端配置了激进的超时**

第 3 条正是本项目的情况：`DialTimeout = 3s` 且
`Read/WriteTimeout = 1s`（`main.go:281-283`），
而 `Check()` 的 ctx 超时仅 200ms（`limiter.go:92`）。

影响评估：本项目使用默认 `ConnPool` 且**不使用 pipeline、不使用 sticky 连接**
（每次 `Run` 从池取用后归还）。按官方公告，这种用法下
「连接归还时会检查读缓冲，因未读数据被标记为坏连接，
故最多出现一次乱序响应后连接即被丢弃」。

严重度 Low（CVSS 3.7）。但对限流网关而言，
**一次乱序响应意味着一次错误的限流判定** —— 可能错误放行或错误拒绝，
且属于典型的沉默逻辑错误（无报错、无崩溃、只是判错）。

## Decision

**立即措施（零风险，本轮实施）：**

在 `newRedis()`（`main.go:270`）设置 `DisableIndentity: true`。

这是官方公告明确给出的 workaround：
"You can prevent the vulnerability by setting the flag `DisableIndentity` to `true`"。
该字段确实存在于 v9.5.3 的 `Options`（已核对 `options.go`，
注意官方拼写错误 Indentity，非 Identity）。

副作用：Redis 侧 `CLIENT INFO` 不再显示客户端库名与版本。
对运维排障有轻微影响，但换取的是消除一类静默判定错误，取舍明确划算。
同时省掉每次建连的一次 `CLIENT SETINFO` 往返，对连接建立略有正收益。

**升级依赖（建议本轮或紧随其后）：**

升级至 `v9.6.3` 或更高（同时脱离 retracted 版本并修复该漏洞）。
需重新生成 `go.sum` 并跑全量回归。
之所以不与 workaround 二选一而是两者都做：`DisableIndentity` 是
行为层面的规避，升级才是根治；且升级需要回归验证窗口，
workaround 可立即生效。

**约束**：升级不得跨 major，不得引入其他依赖变更。
按「幻觉依赖/接口存在性核验」纪律，升级后必须
`go build ./...` + 全量测试通过才算完成，不得凭印象假定 API 兼容。

## Consequences

**正面**

- 消除一类可能导致错误限流判定的沉默逻辑错误。
- 脱离已被官方撤回的依赖版本。
- 略微降低连接建立开销（少一次 `CLIENT SETINFO` 往返）。

**负面**

- `CLIENT INFO` 不再显示客户端标识，Redis 侧排障时无法直接区分
  连接来自哪个客户端库版本。可通过连接来源 IP 与端口区分，影响可接受。
- 版本升级需回归窗口。v9.5.3 → v9.6.3 属 minor 升级，
  按 semver 应无破坏性变更，但仍须实测验证而非假定。

**强制配套验收**

- `go build ./...` 通过。
- 全部单元测试绿（含限流内核 13 项零跳过）。
- `bash test/e2e/run.sh` 50/50 全通过。
- Redis 连接建立与熔断行为无回归（`redis_breaker_open` 保持 0）。
