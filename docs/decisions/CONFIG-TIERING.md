# 配置分层与归属（部署优化的判断依据）

> 用户诉求：①能默认的就默认，减少部署时必填项 ②部分配置搬进管理页面
> 判断标准不是「方便不方便」，而是「能否安全热更新」+「误配的爆炸半径」

---

## 分层原则

| 层 | 判据 | 归属 | 变更方式 |
|----|------|------|----------|
| **Tier 0 · 引导参数** | 进程启动前必须确定，或改动需重建连接/监听 | 环境变量，且**部分必须无默认值** | 重启 |
| **Tier 1 · 运行策略** | 可安全热替换，误配影响可逆，且运维确有调整需求 | **管理页面**（SQLite SoT + 热更新） | 页面即时生效 |
| **Tier 2 · 业务规则** | 已实现的动态数据 | 管理页面（已有） | 页面即时生效 |

---

## Tier 0 · 引导参数（保留环境变量）

### 0-A：必须无默认值 —— 缺失即拒绝启动

> **这是本次最重要的修正。** 当前 compose 给 `ADMIN_TOKEN` 配了默认值
> `change-me-admin-token-32chars-min`，实测用它可访问管理面（HTTP 200）。
> 该值公开写在仓库中，等于管理面无鉴权。
> `ErrNoToken` 只防「忘记设置」，没防住「用了公开占位值」——
> 而占位值更危险，因为它看起来像"已经配好了"。

| 变量 | 现状 | 要求 |
|------|------|------|
| `ADMIN_TOKEN` | compose 默认 `change-me-...`（**可用，实测 200**） | **移除默认值**；启动时校验：非空 + ≥32 字符 + 不在弱值黑名单 |
| `REDIS_PASSWORD` | compose 默认 `unirate_redis_pass` | **移除默认值** |
| `GRAFANA_PASSWORD` | compose 默认 `admin` | **移除默认值** |

**弱值黑名单**至少含：`change-me` 前缀、`admin`、`password`、`test`、`123456`、
`.env.example` 中出现的全部占位值。校验失败必须打印**可操作的**修复指引
（给出生成命令），而不是只说"token too short"。

**降低门槛的正确做法**不是给默认值，而是：
- `make init` 一键生成含强随机凭证的 `.env`（`openssl rand -base64 24`）
- 首次 `docker compose up` 若检测到 `.env` 缺失，明确提示先跑 `make init`

### 0-B：可保留默认值 —— 改动需重建连接或监听

| 变量 | 默认 | 为何不能进管理页面 |
|------|------|-------------------|
| `PROXY_ADDR` / `OBS_ADDR` | `:8080` / `:9091` | 改监听地址需重建 listener |
| `ADMIN_ADDR` | `127.0.0.1:9090` | 同上；且此默认值是安全设计（防一键部署暴露管理面），**不得放宽** |
| `REDIS_ADDRS` / `REDIS_DB` | `127.0.0.1:6379` / `0` | 改动需重建连接池 |
| `STORE_DSN` | 空（落本地 `data/unirate.db`） | 库文件路径在 `store.Open` 时确定，改动需重开连接 |
| `REDIS_POOL_SIZE` | `256` | 池大小需重建连接池 |
| `ADMIN_ALLOW_CIDRS` | compose 给内网网段 | **刻意留在环境变量**：若可从页面改，攻击者拿到令牌后能自行放开来源限制，等于自毁第二重防线 |
| `VERSION` / `LOG_LEVEL` | `dev` / `info` | LOG_LEVEL 可考虑升 Tier 1（见下） |

## Tier 1 · 运行策略（建议搬进管理页面）

前置改造：`proxy.Handler.opt` 当前是值类型、`New()` 时固化，需改为
`atomic.Pointer[Options]` 无锁热替换。项目已在 `config.Store` 用过这个模式，可复用。

| 变量 | 默认 | 搬迁理由 | 风险与护栏 |
|------|------|----------|-----------|
| `EXPOSE_RULE_NAME` | `true` | 外网部署需关（429 响应泄露规则名），内网排障需开。**典型的"环境不同取值不同"** | 无副作用，纯响应头开关 |
| `UPSTREAM_TIMEOUT` | `60s` | 不同业务域上游耗时差异大，调参需求真实 | 设上下限 `1s ~ 600s`；**注意 SSE 不受此约束**（流式不设整体超时） |
| `TOKEN_FLUSH_INTERVAL` | `1s` | 直接影响 Token 超卖窗口，需按业务容忍度调 | 下限 `100ms`（过小则 Redis 压力陡增）；上限 `10s`（过大则超卖窗口过宽） |
| `MAX_REQUEST_BODY_MB` | `32` | 不同业务域请求体大小差异大 | 上限 `256MB`，防内存耗尽 |
| `CONFIG_POLL_INTERVAL` | `15s` | Pub/Sub 兜底轮询频率，权衡时效与负载 | 下限 `5s`，上限 `300s` |
| `LOG_LEVEL` | `info` | **排障刚需**：线上出问题时临时开 debug，重启会丢现场 | 仅 4 个枚举值；debug 需提示"高流量下日志量激增" |
| `INSTANCES` | `1` | 影响降级时的本地保守配额计算（总量÷实例数） | ≥1；**误配会直接影响限流精度**，需二次确认 |

### 明确不搬（即使技术上可行）

| 变量 | 不搬原因 |
|------|----------|
| `ADMIN_ALLOW_CIDRS` | 见上，自毁防线 |
| `TRUSTED_PROXY_HOPS` | 影响 IP 提取，误配导致**限流维度整体错乱**（所有 IP 被识别为同一个）。默认 0（完全不信任 XFF）是安全侧，从页面改容易被误设 |
| `REAL_IP_HEADER` | 同上 |
| `TOKEN_HEADERS` | 影响 token 维度提取，误配使配额统计失效 |
| `ALLOW_HEADER_UPSTREAM` | **SSRF 开关**，默认 false。可从页面开启等于把 SSRF 防线交给一个令牌 |
| `UPSTREAM_ALLOWLIST` | 同上，SSRF 白名单 |
| `TZ_OFFSET_SECONDS` | 影响窗口边界计算，运行中改动会导致计数器窗口错乱 |
| `SHUTDOWN_GRACE` | 仅在退出时读取，页面改无意义 |

## 落地要求

1. **Tier 1 配置需持久化到 SQLite**，走既有 `SQLite(SoT) → Redis → 本地 atomic.Pointer` 链路，与业务规则一致，不新造机制
2. **每次变更写审计日志**（复用既有 `audit_log` 表），管理面无审计等于无问责
3. **每项都要有上下限校验**，且校验在**写入前**完成（复用 `/admin/rules/validate` 的设计思路）
4. **页面必须显示"当前值 / 默认值 / 是否被覆盖"**三态，让运维知道自己改了什么
5. **环境变量与页面配置的优先级必须明确**：建议页面配置优先（因为它是运行期决策），但页面要显示"此项已被环境变量固定"的情形以免困惑
