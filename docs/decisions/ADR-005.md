# ADR-005: SSE 缓冲区池化与 GC / 运行时参数标定

## Status

Accepted (2026-08-23) — 池化部分；GOMEMLIMIT 部分需部署侧配合

## Background

### SSE 缓冲区

`internal/proxy/stream.go:51` 为每条 SSE 流分配一个 16 KB 读缓冲：

```go
br := bufio.NewReaderSize(body, 16*1024)
```

在「高并发 SSE 长连接」这个明确优化目标下，这是每流一次的固定分配。
容器内实测（120 帧典型 LLM 响应，arm64, GOMAXPROCS=4）：

| 基准 | ns/op | B/op | allocs/op |
|---|---|---|---|
| `copySSE` 现状（串行） | 6,683 | 16,416 | 2 |
| `copySSE` 池化（串行） | 4,101 | 32 | 1 |
| `copySSE` 现状（并行） | 4,161 | 16,417 | 2 |
| `copySSE` 池化（并行） | **1,503** | **36** | 1 |
| 单次 `bufio.NewReaderSize(16KB)` | 2,329 | 16,384 | 1 |
| `sync.Pool` Get/Reset/Put | **15.86** | 0 | 0 |

并行场景 **2.8x 提速，分配从 16,417 B 降至 36 B（−99.8%）**。
16 KB 属于 Go 的大对象区间，分配成本（2,329ns）本身就占了串行总耗时的 35%。

### 运行时参数

`docker-compose.yml` 未设置任何 CPU/内存 limit，也未设 `GOMEMLIMIT` / `GOMAXPROCS`
（实测容器内两者均为空，`nproc = 5`）。
Redis 侧已设 `maxmemory 512mb` + `volatile-lru`，网关侧无对应约束。

## Decision

### 一、SSE 读缓冲池化

用 `sync.Pool` 复用 `*bufio.Reader`，在 `copySSE` 入口 `Get` + `Reset(body)`，
退出时 **`Reset(nil)` 后再 `Put`**。

`Reset(nil)` 是强制要求，不是可选项：不断开对 `resp.Body` 的引用会让
池化对象持有已关闭的连接与其底层缓冲，在长连接场景下造成内存无法回收
—— 这会把一个内存优化变成内存泄漏。

**不改变任何流式语义**：缓冲区只是读取侧的临时载体，
`ReadSlice('\n')` 逐行读取 + 每帧 `Flush()` 的行为完全不变。
写入侧（`w.Write(line)` → `flusher.Flush()`）**一行代码都不动**。
这满足「不得破坏 SSE 零缓冲语义」的硬约束 ——
池化的是**上游读缓冲**，不是下游写缓冲，不引入任何攒包。

### 二、GOMEMLIMIT / GOMAXPROCS 标定规则

按 go.dev/doc/gc-guide 官方建议：

**GOMEMLIMIT** — 适用条件是「执行环境完全可控且 Go 程序是内存的唯一使用者」，
容器化网关正好符合。规则：

```
GOMEMLIMIT = 容器内存 limit × 0.9      （官方建议留 5-10% 余量）
```

必须**同时给容器设内存 limit**，否则 GOMEMLIMIT 无基准可依。
当前 compose 未设 limit，属部署侧缺口。

**GOGC 保持默认 100，不设 off。** 官方明确警告：
`GOGC=off` 仅在独占内存时适用，且一旦 live heap 逼近 limit 会触发
**GC 抖动（thrashing）** —— 程序不 OOM 但无限期停滞，
「多数情况下比 OOM 更糟，因为 OOM 至少失败得快」。
网关是基础设施组件，可用性优先于内存经济性，不接受抖动风险。

**GOMAXPROCS 不显式设置。** 项目 `go.mod` 声明 `go 1.22`，
Go 1.25 的容器感知 GOMAXPROCS 对本项目**不生效**
（该行为要求 go.mod 声明 go 1.25+）。
但当前 compose 也未设 CPU limit，不存在 cgroup quota 与 `NumCPU()` 的错配，
因此**现状无问题**。

**这是一条必须写入部署文档的前置条件**：
若未来给容器设 CPU limit（如 K8s `limits.cpu: 2`）而仍用 Go 1.22 构建，
`GOMAXPROCS` 会取宿主核数导致 CFS throttling 与 p99 尖刺。
届时二选一：显式设 `GOMAXPROCS` 环境变量匹配 limit，或引入
`go.uber.org/automaxprocs`。**不要等出问题才发现。**

### 三、pprof 端点（诊断能力，非优化本身）

在 `ObsAddr`（`:9091`，仅内网）挂载 `net/http/pprof`，由环境变量开关控制，
默认关闭。理由：本轮所有优化结论都来自离线基准，
缺少生产侧 heap/CPU profile 就无法验证优化在真实流量下是否成立
（gc-guide 的第一步就是「用 CPU profile 确认 GC 真的是主要成本」）。

**安全约束**：绝不挂在 `ProxyAddr`。pprof 会暴露内存内容与 goroutine 栈，
且 `/debug/pprof/profile` 可被用于 CPU 耗尽型 DoS。
`ObsAddr` 当前无鉴权，故必须默认关闭 + 显式开启 + 文档标注仅限内网。

## Consequences

**正面**

- 每条 SSE 流省 16 KB 分配。1 万并发流场景下峰值分配减少约 **160 MB**，
  这是「高并发 SSE」目标下最直接的内存收益。
- SSE 转发 CPU 并行场景 −64%（4,161ns → 1,503ns/120 帧）。
- 分配率下降按 gc-guide 摊销模型直接降低 GC CPU 成本。
- GOMEMLIMIT 提供 OOM 保险，避免瞬时堆尖峰打爆容器。

**负面**

- `sync.Pool` 池化对象在 GC 时会被清理，突发流量下仍有分配 —— 这是 `sync.Pool`
  的设计特性，不是缺陷；稳态复用率足够高即达到目的。
- 必须严格执行 `Reset(nil)`，否则从内存优化变成内存泄漏。
  这是**代码评审必查项**，需在 PR 中显式确认。
- GOMEMLIMIT 设置过低会触发 GC 抖动（官方明确的 death spiral 风险）。
  必须配合容器 limit 一起设，且留 10% 余量，不可单独设置。
- pprof 端点扩大攻击面，靠「默认关闭 + 仅内网 + 文档」三重约束控制。

**强制配套验收**

- SSE 相关测试（`internal/proxy/stream_test.go`）全绿。
- e2e 中 SSE 首字节延迟与总流时长须与优化前持平
  （基线：首字节 5ms / 总流 2000ms）；
  **任何首字节延迟上升都说明引入了攒包，必须回退。**
- 并发 SSE 流场景 `-race` 无竞争，`sse_streams_active` 正确归零。
