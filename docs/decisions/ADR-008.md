# ADR-008: 压测方案设计与优化前后可比性保证

## Status

Accepted (2026-08-23)

## Background

本轮所有优化结论均来自离线微基准。微基准能证明「某段代码变快了」，
**不能证明「网关吞吐提高了」** —— 端到端瓶颈可能完全在别处
（实测表明 Redis 100% 跑满单核、真实脚本约 31k QPS 饱和，这是真正的天花板）。

因此必须有端到端压测作为验收闸门。且压测必须解决一个核心问题：
**优化前后的数据如何保证可比。** 否则「提升了 30%」这类结论毫无意义。

现有 `test/e2e/run.sh` 是**功能验收**（50 项断言），不是性能压测，
两者不可混用。

## Decision

### 一、工具选型：自写 Go 程序（原定 k6 已废弃）

**决定：用 Go 标准库自写压测程序 `test/perf/loadgen`，不用 k6。**

废弃 k6 的直接原因：**镜像拉不下来**。实测
`docker pull grafana/k6:latest` 在本项目网络环境下持续重试超时，
方案不可执行。本机 `hey`/`wrk`/`vegeta`/`k6` 均未安装且同样受限于网络。

自写方案的额外收益（不只是退而求其次）：

| 维度 | 说明 |
|---|---|
| 离线可跑 | 零第三方依赖（仅标准库 + 自写极简 RESP 客户端），内网无 GOPROXY 也能 `go run` |
| 判据内建 | 预热、5 轮中位数、双侧 CPU 归因、四类硬断言直接编码进程序，不靠人工比对 |
| SSE 语义精确 | 与被测服务同语言，可精确识别首个 `data:` 帧以测 TTFB，通用工具难做到 |
| 产物可比 | 输出结构化 JSON 基线，含环境声明与归因结论，避免「裸数字」被误用 |

代价：需自行维护约 2000 行压测代码；已按单文件 ≤300 行拆分为
9 个文件（采集/判定/场景/报告分离）。

**运行方式**（`test/perf/run.sh` 已封装）：

```bash
bash test/perf/run.sh A          # 单场景
bash test/perf/run.sh all        # 四场景
LABEL=after-opt bash test/perf/run.sh A   # 打标签做前后对比
QUICK=1 bash test/perf/run.sh A  # 快速验证程序本身（不可作基线）
```

**职责分工**（这是必须的，不是设计偏好）：
- **宿主侧 shell** 采集容器 CPU —— 压测程序在容器内**拿不到 docker socket**，
  无法调 `docker stats`；而双侧 CPU 是归因的强制依据。
- **容器内 loadgen** 施压 + 采集客户端分位数、`/metrics`、Redis `commandstats` + 判定。

**关键约束**：压测客户端与网关必须同网络但**不同容器**，
且需给客户端容器足够 CPU —— 否则测的是客户端瓶颈。
`ab` 单线程模型在 >10k QPS 时会先于网关饱和，**不可用于正式结论**。

### 一之二、压测环境必须先解除限流天花板（实测踩坑）

吞吐场景**不能直接打 `demo`**，否则测到的是拒绝路径而非吞吐。
两层配额都要处理，缺一层数据即无效：

1. **biz 级**：`demo` 挂 `limit=10/1s`。首版直接压 demo，
   44 万请求里仅 **210 个 200**、其余全 429，却报出「2.2 万 QPS」——
   这种数据比没有更危险。故新建 `perft` 业务域，
   规则集与 demo **同构**（fixed + sliding + conc + token 四条）
   以保持脚本成本一致，仅把配额抬到 1e9。
2. **全局级**：`config.Store.Rules()` 会把 `biz="*"` 的规则合并进
   **每一个** biz（见 `internal/config/store.go`），
   而 `global-qps-guard` 是 `limit=5000/1s`。
   只抬 `perft` 无效 —— 实测 200 占比仍仅 **38.99%**，
   3,336,486 次拒绝全部来自该全局规则。
   故压测前临时抬高全局规则、**结束后自动还原**（含失败路径）。

程序内置守卫：吞吐场景 **200 占比 < 95% 即判 FAIL**，
防止「测到拒绝路径」这类错误再次被当作有效结果。
修正后实测 200 占比 **100%**。

### 二、测试场景（4 个，对应双优化目标）

**场景 A — 纯 QPS 吞吐（非流式）**
- 目标：验证 ADR-001/002/003 的准入路径优化
- 配置：`limit` 设足够大（避免测到拒绝路径），4 条规则全开
- 并发爬坡：32 → 128 → 256 → 512 → 1024
- 采集：QPS、p50/p95/p99、错误率

**场景 B — 限流拒绝路径吞吐**
- 目标：验证拒绝路径不退化，且**拒绝精度零误差**
- 配置：`limit=50`，500 并发瞬时打入
- **硬断言：通过数恰好 = 50。这是 P0-1/P0-5 的回归闸门，
  任何偏差直接判定优化失败并回退。**

**场景 C — 高并发 SSE 长连接**
- 目标：验证 ADR-005 的池化收益与零缓冲语义
- 配置：并发流数 100 → 500 → 1000 → 2000，每流 120 帧、20ms 帧间隔
- 采集：**首字节延迟（TTFB）**、总流时长、
  `sse_streams_active`、容器 RSS、goroutine 数
- **硬断言：TTFB 不得高于基线（5ms）。上升即说明引入攒包，立即回退。**

**场景 D — 混合流量**
- 目标：贴近真实（LLM 网关同时承载流式与非流式）
- 配置：70% SSE + 30% 非流式，持续 5 分钟
- 采集：稳态 RSS 曲线（查内存泄漏）、GC 频率、`pool_timeouts_total`

### 三、采集指标（三层，缺一层结论不完整）

**客户端侧**：QPS、p50/p90/p95/p99/p999、错误率、TTFB（SSE）

**网关侧**（`/metrics` + pprof）：
- `unirate_request_duration_seconds`（已有直方图）
- `unirate_redis_pool_*`（ADR-004 新增，**判断池是否成为瓶颈的唯一依据**）
- `unirate_redis_breaker_open`（**必须恒为 0** —— 压测期间熔断说明
  优化引入了不稳定，结论无效）
- `unirate_redis_errors_total`、`unirate_concurrency_in_flight`
- goroutine 数、heap inuse、GC 次数与累计暂停（pprof / `runtime/metrics`）

**依赖侧**：
- Redis `INFO commandstats` 的 `cmdstat_evalsha`（calls / usec_per_call）
  —— 用于判断瓶颈是否已转移到 Redis
- Redis `INFO cpu`、`connected_clients`
- 容器 `docker stats` CPU% / MemUsage

### 四、可比性保证（本 ADR 的核心）

**这一节是压测有效性的全部前提，逐条都是硬要求：**

1. **同一物理环境、同一 compose 拓扑**。不跨机器、不跨时段对比。
   本机同时运行着 20+ 无关容器（实测 `docker ps`），
   压测前必须记录 `docker stats` 全局快照；
   邻居容器负载差异过大的两次测量**不可比**。

2. **每轮前重置状态**：
   - `FLUSHDB` 清空 Redis 限流键（残留计数器会污染判定）
   - 重启网关容器（清空本地负缓存、连接池、GC 状态）
   - 固定配置版本（记录 `unirate_config_version`）

3. **预热强制执行**：每轮正式采集前跑 30s 丢弃数据。
   依据：EVALSHA 需要脚本已加载（实测冷启动 `cmdstat_eval` 173µs/call
   vs 热态 `evalsha` 18.78µs/call，**9 倍差异**）；
   连接池需达到稳态；Go 运行时需完成初期 GC 周期。
   **不预热的对比数据一律作废。**

   冷热差实测（同一 Redis 累积统计，`INFO commandstats`）：
   `cmdstat_eval` 144.67µs/call（6 次，冷路径：脚本首次加载编译）
   vs `cmdstat_evalsha` 3.56µs/call（105 万次累积）。
   **注意这两个数字不能直接相除得出「冷热差 40 倍」** ——
   `eval` 与 `evalsha` 的累积样本来自**不同脚本**（前者含首次加载的
   3 个正式脚本，后者绝大部分是简化探针），分母口径不同。
   可确认的结论是：**冷路径首次 EVAL 是百微秒量级，
   热路径 EVALSHA 是个位数到二十几微秒量级，差一个数量级以上**，
   这已足够支撑「必须预热」这一要求，无需精确倍率。

4. **多轮取中位数**：每场景每并发档跑 5 轮，取中位数而非最优值。
   实测同配置下 QPS 波动可达 ±8%（简化探针 PoolSize 128 与 256 的
   88,288 vs 87,804 即在噪声范围内），单轮数据不足以支撑结论。

5. **变量隔离**：一次只改一项优化。
   ADR-001/002/003/005 分别独立测量，最后测叠加效果。
   否则无法归因，也无法在某项拖后腿时定位。

6. **基线固化**：优化前的完整数据集提交到仓库
   （`test/perf/baseline/` 下，JSON 格式 + 环境快照），
   作为可寻址产物而非只活在会话里。

7. **判定阈值预先声明**（避免事后找解释）：
   - 场景 A 吞吐提升 < 10% → 该项优化不值得保留其复杂度
   - 场景 B 拒绝精度有任何偏差 → 立即回退
   - 场景 C TTFB 上升 → 立即回退
   - 任何场景 `breaker_open` > 0 或错误率上升 → 结论无效，重测

### 五、已建立的参考基线（本轮实测，可直接复用）

**必须用真实 `batch_check.lua` 测量。** 首版基线曾用简化探针脚本
（3.70µs/call）得出 88k 平台期，该数字**不适用于容量规划、已作废**
—— 真实脚本贵 6 倍，平台期约 31k。这是本轮复核纠正的主要偏差。

真实 `batch_check.lua`（4 规则，与 demo 生产配置一致）：

| 指标 | 实测值 |
|---|---|
| 单次脚本成本 | **22.3 µs/call**（简化探针仅 3.70，勿混用） |
| 单往返饱和吞吐 | **约 31,000 QPS**（conc 64→1024 恒为 30.6k-31.3k） |
| 双往返饱和吞吐 | 约 22,400 QPS |
| **Redis CPU（饱和时）** | **0.998-0.999 核 = 100% 跑满单核** |
| 压测客户端 CPU | 0.64-0.70 核（**未饱和，非瓶颈**） |
| p50 / p99（256 并发） | 8.07ms / 16.15ms |
| p50 / p99（512 并发） | 15.91ms / 24.02ms |

**容量公式**：
`端到端 QPS 上限 ≈ 1,000,000 ÷ 脚本µs/call ÷ 每请求往返数`
（22.3µs：单往返 → 31k，双往返 → 22.4k，均与实测吻合）。
**该值随规则数变化，容量规划须用目标业务的真实规则集实测。**

**归因方法（每轮压测必做，不可省）**：
同步采集 Redis 容器 CPU 与压测客户端 CPU。判据：

- Redis 跑满单核 + 客户端未饱和 → 瓶颈在 Redis（当前状态）
- Redis 未跑满 + 客户端跑满 → **瓶颈在客户端，数据无效，须加客户端资源重测**
- 两者都未跑满 → 瓶颈在 gateway 或网络，需 pprof 定位

**没有双侧 CPU 数据的压测结论不予采信** —— 这正是首版 88k 归因失准的根因。

### 六、已固化的 before-opt 基线（本机实测）

产物：`test/perf/baseline/*-before-opt.json`（含环境声明与归因结论）。

**场景 B（拒绝路径精度，5 轮）—— 关键闸门，PASS**

| 指标 | 结果 |
|---|---|
| 500 并发打 limit=50 | **5 轮全部恰好通过 50 个，零误差** |
| `redis_breaker_open` | 全轮次 0 |
| 传输错误 | 0 |

这是 P0-1（配额放大）与 P0-5（计数器污染）的回归闸门，
优化后必须仍为 50，任何偏差立即回退。

**场景 A（纯吞吐，5 轮 × 3 并发档）**

| 并发 | QPS 中位数 | 离散度 | p50 | p99 | Redis 核数 |
|---|---|---|---|---|---|
| 64 | 约 9,900 | 24.6% | 8.9ms | 30ms | 0.72 |
| 256 | 7,207 | 29.5% | 32.31ms | 91.94ms | 0.657 |
| 512 | 8,841 | 39.9% | 55.38ms | 107.27ms | 0.788 |

200 占比 **100%**（1,885,263 个 200，0 个 429）—— 确认测的是成功路径。

**这组数据的可信度限制（必须明确）**：
离散度 24-40% 远超 ADR-008 定的 20% 阈值，程序据此判 FAIL，**这是正确的**。
归因显示 Redis 73.1%、gateway 153.6%，**两侧均未饱和**，
说明瓶颈在压测客户端与被测服务争抢同一批 5 核。
因此**场景 A 的绝对 QPS 不可作容量参考**，
只可用于同环境、同参数的优化前后对比，且需关注离散度是否同量级。
若需权威吞吐数字，必须在客户端与服务分离的专用环境复测。

注：场景 A 实测 QPS（7-10k）远低于我此前用独立探针测得的
「单往返约 31k」—— 两者口径不同，不矛盾：
探针只打 Redis，而场景 A 走完整链路（HTTP 解析 + 规则求值 +
Redis 往返 + 转发上游 mock + 响应回写），且客户端与服务争抢 CPU。
**端到端 QPS 低于 Redis 理论上限是正常的**，
这也再次说明单一数字必须附带口径说明才有意义。

## Consequences

**正面**

- 优化收益有端到端数据支撑，不停留在微基准。
- 拒绝精度与 SSE TTFB 作为硬闸门，防止性能优化悄悄牺牲正确性
  —— 这正是「沉默逻辑错误」最可能的入口。
- 基线固化后，未来任何改动都可对比，形成持续的性能回归能力。

**负面**

- 需新增并长期维护 `test/perf/`（约 2000 行 Go，9 个文件）。
  已作为独立 module（`unirate/perf/loadgen`）与主工程隔离：
  仓库根的 `go build ./...` / `go test ./...` 会跳过含自身 go.mod 的子目录，
  实测 `go list ./...` 下 grep perf 得 0 条，压测代码不可能污染主工程。
- 5 轮 × 4 场景 × 多并发档的完整压测耗时较长（估计 2-3 小时/完整轮）。
  可在开发期只跑场景 A + B 快速反馈，完整套件在合并前跑一次。
- 本机存在大量无关容器，环境噪声无法完全消除，
  只能靠「同环境 + 多轮中位数」缓解。**若需权威数据，应在专用环境复测。**
