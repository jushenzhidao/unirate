# ADR-004: 连接池参数标定方法论与池指标可观测化

## Status

Accepted (2026-08-23)

## Background

现状参数（`cmd/gateway/main.go:270-286`、`config/env.go:114`）：

| 参数 | 现值 | 来源 |
|---|---|---|
| `PoolSize` | 256（`REDIS_POOL_SIZE` 可配） | 拍定 |
| `MinIdleConns` | 16 | 拍定 |
| `PoolTimeout` | 1s | 拍定 |
| `ConnMaxIdleTime` | 5min | 拍定 |
| `DialTimeout` | 3s | 拍定 |
| `Read/WriteTimeout` | 1s | 拍定 |
| `MaxRetries` | 2 | 拍定 |

SoT 池：本 ADR 撰写时为 MySQL（`MaxOpenConns 16` / `MaxIdleConns 8` /
`ConnMaxLifetime 30min`）。SoT 已切换为进程内嵌 SQLite，池配置随之改为
单连接，详见「四、SoT 池（SQLite）」。

核心问题不是数值对不对，而是**池饱和时完全不可观测**。
`obs/metrics.go` 的 13 项指标里没有任何一项反映连接池状态。
go-redis 的 `UniversalClient` 接口本身就暴露了 `PoolStats() *PoolStats`
（已核对 v9.5.3 `universal.go`），拿不到数据不是技术限制，是没接。

这个盲区是危险的：池打满时 `waitTurn` 会阻塞至 `PoolTimeout`（1s），
而 `Check()` 的 ctx 超时只有 200ms（`limiter.go:92`），
于是**池饱和会先表现为 Redis 超时**，再被熔断器
（`limiter.go:243-247`）计为「Redis 故障」。
代码注释（`main.go:275-277`）其实已经预见了这一点，但没有配套指标去证实它。

## Decision

### 一、池指标必须暴露（本 ADR 的硬性部分）

新增 5 项指标，数据源为 `rdb.PoolStats()`，在既有 `runtimeStateLoop`
（`main.go:234`，5s ticker）内同步：

| 指标 | 类型 | 源字段 | 告警语义 |
|---|---|---|---|
| `unirate_redis_pool_total_conns` | gauge | `TotalConns` | 接近 PoolSize 即饱和预警 |
| `unirate_redis_pool_idle_conns` | gauge | `IdleConns` | 长期为 0 = 池不足 |
| `unirate_redis_pool_timeouts_total` | counter | `Timeouts` | **> 0 即池不足，必须告警** |
| `unirate_redis_pool_misses_total` | counter | `Misses` | 增速高 = 池抖动/复用差 |
| `unirate_redis_pool_stale_conns_total` | counter | `StaleConns` | 异常高 = 空闲超时配置不当 |

SoT 侧同理暴露 `db.Stats()` 的 `WaitCount` / `WaitDuration` / `InUse` / `Idle`。
SoT 为单连接 SQLite，这几项衡量的是写操作串行排队深度（见第四节）。

`Timeouts` 与 `Misses` 在 go-redis 中是**单调累积的 uint32**
（`internal/pool/pool.go` 用 `atomic.AddUint32`），
直接 `Set` 到 gauge 会丢失 Prometheus 的 `rate()` 语义，须按 counter 处理。
注意 uint32 存在理论回绕，实施时按「取差值累加到 int64 counter」处理。

### 二、PoolSize 标定规则（不是给数字，是给推导）

**规则 1 — 上界由 Redis 吞吐天花板决定，不由并发数决定。**

> **口径修正（重要）**：下表用的是**简化探针脚本**（实测 3.70µs/call），
> 故平台期落在 87-88k。**真实 `batch_check.lua` 为 22.3µs/call（贵 6 倍），
> 实测平台期约 30,000-31,000 QPS** —— 见「规则 1b」。
> 下表仍有价值：它证明「PoolSize 超过某值后吞吐不再增长」这一**形状规律**，
> 该规律与脚本复杂度无关。但**绝对数值不可用于容量规划**。

实测（Redis 7.2 单实例，同 Docker 网络，EVALSHA 预热后，固定 512 并发，简化脚本）：

| PoolSize | QPS | p50 | p99 | Misses | Timeouts |
|---|---|---|---|---|---|
| 8 | 67,779 | 7.36ms | 10.10ms | 0 | 0 |
| 16 | 83,215 | 6.05ms | 7.48ms | 0 | 0 |
| 32 | 87,191 | 5.73ms | 7.95ms | 1 | 0 |
| 64 | 87,664 | 5.70ms | 7.98ms | 32 | 0 |
| 128 | 88,288 | 5.59ms | 11.85ms | 96 | 0 |
| 256 | 87,804 | 5.43ms | 8.57ms | 224 | 0 |
| 512 | 80,957 | 4.75ms | 12.26ms | 480 | 0 |

**PoolSize ≥ 32 后吞吐完全持平（87-88k），512 反而回落至 81k 且 p99 恶化。**

原因是 Redis 单线程：超过饱和点后增加连接只是把排队从客户端搬到服务端，
并放大 p99 尾延迟。**PoolSize 的作用是「不成为瓶颈」，而非「越大越快」。**

**规则 1b — 真实脚本的容量基线（用这一组做容量规划）**

用真实 `batch_check.lua`（4 条规则，与 demo 生产配置一致）实测，
`CONFIG RESETSTAT` 后受控负载 + 400 次预热 + 双侧 CPU 同步采集：

| 并发 | QPS | p50 | p99 | evalsha µs/call | **Redis 核数** | 客户端核数 |
|---|---|---|---|---|---|---|
| 64 | 32,619 | 1.82ms | 3.75ms | 21.67 | **0.999** | 0.696 |
| 256 | 30,577 | 8.07ms | 16.15ms | 21.93 | **0.998** | 0.640 |
| 512 | 31,067 | 15.91ms | 24.02ms | 21.76 | **0.998** | 0.655 |
| 1024 | 31,303 | 32.03ms | 40.41ms | 21.59 | **0.998** | 0.665 |

**归因结论（本次复核的核心产出）**：
Redis CPU 在**所有并发档恒为 0.998-0.999 核，即 100% 跑满单核**，
而客户端仅 0.64-0.70 核。**瓶颈确凿在 Redis 单线程，不在客户端、不在 gateway。**
QPS 从 conc=64 到 1024 完全不增长（32.6k→31.3k）而 p50 涨 17.6 倍
（1.82ms→32.03ms），是教科书式的饱和曲线。

交叉校验：`30,577 QPS × 21.93µs = 0.671 核`，
与 `INFO cpu` 实测的 0.998 核吻合（差额为网络 I/O、认证、连接管理开销）。
两个独立数据源相互印证，归因成立。

**修正后的容量公式**：

```
端到端 QPS 上限 ≈ 1,000,000 ÷ (单次脚本 µs/call) ÷ 每请求往返数

真实 batch_check（4 规则，22.3µs）：
  单往返 → 约 31,000 QPS（实测 30.6k-31.3k，吻合）
  双往返 → 约 22,400 QPS（实测 21.8k-22.4k，吻合）
```

**该公式随规则数变化** —— 规则越多脚本越贵，上限越低。
容量规划必须用**目标业务的真实规则集**实测，不可套用本表。

**规则 2 — 推导公式（Little's Law）**

```
单实例所需连接数 ≈ 目标QPS_单实例 × 单次往返耗时(s)

例：目标 20k QPS/实例，Redis 往返 p50 = 0.3ms（低负载实测 ~98µs~209µs，
    取含排队的保守值）
    → 20000 × 0.0003 = 6 条连接

再乘安全系数（应对突发与尾延迟）：
    PoolSize = ceil(理论值 × 4) ，并设下限 32、上限 128
    → max(32, 6×4) = 32
```

安全系数取 4 而非 2 的依据：p99/p50 比值在实测中约 1.5-2.2，
另需覆盖 GC 停顿与网络抖动导致的瞬时排队。

**规则 3 — 集群总量约束（必须校验，否则会打爆 Redis）**

```
实例数 × PoolSize + 其他客户端连接 < Redis maxclients × 0.8
```

当前 `maxclients = 10000`（实测 `INFO clients`），
故 `实例数 × PoolSize < 8000`。
按 PoolSize=128 计算，最多支撑 62 个网关实例。
**这条约束在多实例扩容时必须复核 —— 它是硬上限，超过会导致新连接被拒。**

**规则 4 — 结论：现状 256 偏大但无害，建议降至 128。**

依据：32 已达吞吐平台，128 留足突发余量，且把集群实例上限从 31 抬到 62。
但**这属于低优先级调整** —— 实测 256 与 128 吞吐差异在噪声范围内（87.8k vs 88.3k），
真正该做的是先上指标，用 `pool_timeouts_total` 与 `idle_conns` 说话。
无数据支撑的参数调整只是把一个魔数换成另一个魔数。

### 三、超时参数一致性约束（发现的真实隐患）

必须满足：`PoolTimeout < REDIS_TIMEOUT`，否则池等待会先撞上 ctx 超时，
使「池不足」伪装成「Redis 故障」并触发熔断降级。

现状 `PoolTimeout = 1s` 而 `REDIS_TIMEOUT = 200ms`（`env.go:115`），
**违反该约束**。建议 `PoolTimeout` 设为 `REDIS_TIMEOUT` 的 50%（100ms），
让池不足以 `ErrPoolTimeout` 形态快速失败并被 `pool_timeouts_total` 计数，
而不是伪装成 Redis 故障。

注：go-redis 的 `PoolTimeout` 默认值为 `ReadTimeout + 1s`
（已核对 v9.5.3 `options.go` 的 `init()`），显式设置后不受默认逻辑影响。

### 四、SoT 池（SQLite）

**本节原为 MySQL 池调优，已随 MySQL 移除失效。** SoT 改为进程内嵌 SQLite
（`store/store.go`）后，池的调优空间基本消失：

`MaxOpenConns(1)` / `MaxIdleConns(1)` / `ConnMaxLifetime(0)` —— 单连接是
**刻意选择**，不是保守配置。SQLite 在 WAL 模式下仍只允许单写者，放开并发连接
只会把冲突从「Go 侧排队」变成「SQLITE_BUSY 自旋重试」，后者更难观测。
`ConnMaxLifetime(0)`（不过期）同理：本地文件连接没有网络中断风险，
定期重建只是无谓开销。

因此原「补 `SetConnMaxIdleTime`」「等 `WaitCount` 数据再调 `MaxOpenConns`」
两条决策**均已作废**。`db.Stats()` 的 `WaitCount` / `WaitDuration` 仍值得暴露，
但语义变了：它现在衡量的是**写操作串行排队深度**，而非连接池容量不足。
配置读写是低频操作（Bootstrap + 15s 轮询 + Admin 写入），单连接足够；
若 `WaitDuration` 显著上升，正确的应对是排查慢事务，而不是加连接。

## Consequences

**正面**

- 池饱和从「不可见」变为「可告警」，消除「池不足被误判为 Redis 故障」的诊断盲区。
- `PoolTimeout` 修正后，池不足与 Redis 故障在指标上可区分，
  熔断器不再被池问题误触发。
- 标定公式可复用于扩容决策，不需要每次重新拍数字。

**负面**

- `PoolStats()` 每 5s 调用一次，开销可忽略（读几个原子变量）。
- 新增 5+4 项指标会增加 `/metrics` 体积。实测当前 8043 B / 113 行，
  新增约 9 行，影响可忽略。
- `PoolTimeout` 调小会让池不足时的失败**更早发生**。这是有意的
  —— 快速失败 + 指标可见，优于慢失败 + 误判为 Redis 故障。
  但需注意：这会让 `pool_timeouts_total` 在池真的不足时快速增长，
  运维需理解该指标语义而非误以为是新故障。
