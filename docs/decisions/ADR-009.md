# ADR-009: 规则校验前移到管理控制台前端，并用 Go 测试守住双端一致性

## Status

Accepted (2026-08-24)

## Background

管理控制台的限流规则表单（`internal/adminui/assets/page-rules-form.js`）目前把
**全部**校验职责交给后端：字段变化后 400ms debounce 调
`POST /admin/rules/validate`，再按 `problems[].index` 回填错误。

这带来三个问题：

1. **反馈延迟**。用户填完一个非法值要等 400ms + 一次网络往返才知道错了。
   编辑一条规则要经历多轮这样的等待。
2. **约束不可见**。`internal/limiter/rule.go:106` `Validate()` 里的若干硬约束
   在界面上零表达，用户只能靠试错发现：
   - `sliding_window && limit > 100000` 被拒（`rule.go:177`）
   - `burst < limit/winSec` 被拒（`rule.go:171`）
   - `d`/`w` 窗口按 `TZ_OFFSET_SECONDS` 自然对齐（`rule.go:96`），非滚动窗口
   - 前端窗口预设与 `README.md:115`、`DESIGN.md:240` 三方互不一致，且
     `WINDOW_SECONDS` 是 6 键固定表，自定义窗口下速率换算直接空白
3. **静默规范化不可知**。`Validate()` 有五个分支不报错但改值
   （`TimeoutSec<=0→120`、`Burst<=0→Limit`、`Watermark 越界→80`、
   `Metric==""→request`、`Algorithm==""→fixed_window`）。用户以为自己填的值
   生效了，实际落库的是另一个值 —— 其中 watermark 直接影响监控看板的
   「接近上限」标记，timeout 影响并发槽释放。

约束前提：控制台是**零构建 / 零 npm / 零 CDN 外链**的原生 JS（见
`internal/adminui/adminui.go:6`），CSP 锁死 `default-src 'none'` 且无 eval。
用户明确要求不影响性能，且无需兼容旧版本前端资产。

## Decision

**一、把 `Validate()` 的全部阻断型校验前移到前端，实时（同帧）反馈；
静默规范化中会真实落库且影响运行行为的三条显式提示。**

新增三个资产：`rule-spec.js`（**纯规格数据，无函数**）、
`rule-validate.js`（纯函数校验器 + `parseWindow` 移植，不碰 DOM）、
`rule-preview.js`（只读 JSON 预览 + 样例键）。边界是「规格是数据，
判定是函数」—— `parseWindow` 同时被 burst 下限校验与速率换算展示依赖，
属校验器内部依赖；`rule-spec.js` 保持纯数据可让 `rulespec_test.go`
的正则抽取面最小、最不易脆。不新建 `rule-semantics.js`：每个新文件
要同步改三处硬门禁（embed 白名单 / index 双向引用 / 加载顺序），
而这些函数在现有三文件里各有天然归属。规范化提示只对 timeout / burst / watermark 三条做，
metric 与 algorithm 两条不做 —— seg 控件恒有选中值，那两个分支不可达，
为不可达分支加提示是纯噪音。

**二、一致性靠 Go 测试机械断言，不靠人工纪律。**

新增 `internal/adminui/rulespec_test.go`。它不执行 JS，而是从嵌入的
`rule-spec.js` 正则抽取字面量，与真值双向比对：

- 与 `limiter` 包导出常量（`Alg*`/`Type*`/`Metric*`/`Dim*`）逐项 + 数量比对
- 与 `rule.go` **源码**里抽出的字面量比对（`100000`、`120`、`80`）
- 窗口单位表**直接调 `limiter.ParseWindow("1"+unit)`** 验证秒数与
  `natural` 标志 —— 复用真实函数，是最强的等价性证明

任一侧改动导致漂移，`go test ./internal/adminui/` 立刻红。

**三、后端校验端点保留，前端不通过时不发请求。**

`POST /admin/rules/validate` 不下线，它仍是权威源、仍负责同 biz 其他规则的
检查、仍在 upsert 写入路径上兜底。改的是调用时机：本地校验有 error 时
**不调**（省掉必然失败的往返），本地通过后才 400ms debounce 调一次确认。
前端通过而后端拒绝时，UI 显式打出「服务端发现前端未拦下的问题」——
这是漂移的唯一运行期信号，不静默吸收。

**四、明确否决的两个替代方案。**

- **Go 侧新增 `/admin/rules/spec` 端点供前端 fetch**：抽屉打开时多一次 RTT，
  或需缓存与失效逻辑；spec 到达前校验器不可用，体验反比现状差。
  而"值同步"用方案二零运行期成本即可达成。
- **go:generate 生成 `rule-spec.js`**：直接违背零构建硬约束，且生成物同步
  又要一个 `git diff --exit-code` 检查，复杂度高于方案二而收益相同。

**五、性能立场：零运行期回退，实际为净改善。**

改动面不含 `internal/limiter` / `internal/proxy`，网关数据面结构性零影响。
浏览器端每键校验是十几个标量比较，微秒级；掉帧风险不在计算而在 DOM 重绘，
故强制「就地更新、禁止 repaint」（沿用 `rule-fields.js:90` 既有模式，
`page-rules-form.js:90` 的注释已记录过失焦这个坑）。JSON 预览是单个
`<pre>` 写 `textContent` + `requestAnimationFrame` 合并，**不做语法高亮**
（需按 token 建节点，与 innerHTML 禁令和性能目标同时冲突）。
admin 端 `validate` 调用量下降。唯一成本是约 22 KB 资产（gzip 约 7.8 KB，
总量 +11%）与约 30 KB 常驻内存，一次性、无请求期开销。

**六、样例键预览按四种 key 结构分支，boundary 段分显真值与占位。**

`internal/limiter/limiter.go:220` 的 switch 有**四**个分支，不是三个：
`type=rate && metric=token` → `TokenLedgerKey`（`tk`，五段）在最前，
其次 `type=concurrency` → `ConcurrencyKey`（`cc`，四段，首段后是 biz），
再 `algorithm=token_bucket` → `TokenBucketKey`（`tb`，**三段**，
无 winSec/boundary，刻意如此 —— 带 boundary 会使桶每窗口重建，
退化成「固定窗口 + 突发额度」，评审 P0-2），default → `RateKey`（`rl`，五段）。
`metric` 判定早于 `algorithm`，故 `metric=token` 的规则永远走 `tk`、
`algorithm` 不参与选键。`sampleKey()` 的分支顺序必须与之逐字一致。

boundary 段按窗口单位分野：`s`/`m`/`h` 的 `natural=false`
（`key.go:78`），纯绝对时间对齐，前端算得百分之百准确，显示真实数字；
`d`/`w` 依赖 `TZ_OFFSET_SECONDS`，而该值未被任何 admin 端点暴露，
故只此一段占位为 `<按业务时区对齐>` —— 不含时区数字或具体时刻，
说明来源而非推算值，且尖括号在 shell 里非法，复制去 SCAN 必然报错，
是刻意的失败前置。`winSec` 段仍显真实数字（与时区无关），不一起占位。

`rulespec_test.go` 增设 key 格式断言（`sep` 为 ASCII `|`、四个前缀、
段数、`maxRawLen=48`、哈希 24 hex、global 空值 `_`），起因是设计稿曾
把分隔符写成全宽 `│`（U+2502）—— 该码位不在 `TestNoEmojiInAssets`
的扫描区间（1F300-1F9FF / 2600-27BF / FE00-FE0F），现有门禁抓不到。

窗口预设定为 `['1s','1m','5m','1h','1d','1w','2w']`（现有六个 + `2w`，
不做替换式移除 —— 移除 `1w` 会让既有 `1w` 规则掉出预设）。`<optgroup>`
分族为 4 滚动 + 3 自然对齐，分族依据是 `parseWindow().natural`
而非硬编码清单，故自定义 `3d` 同样落入自然对齐分支。

## Consequences

**正面**

- 非法组合当帧可见，编辑一条规则的试错轮次从"每轮 400ms + RTT"降到零等待
- 五个此前完全不可见的约束（滑动窗口上限、burst 下限、自然对齐语义、
  自定义窗口速率换算、计数键粒度）在界面上有了表达
- 三条静默规范化对用户可知，落库值不再与预期不符
- `/admin/rules/validate` 请求量下降，admin 端 CPU 与 `Validate()` 调用减少
- 顺带修正 `api.js` 的 `RULE_ERR_MAP`：多条 `^` 锚定正则因后端文案带
  `rule %q:` 前缀而实际匹配不到，前移后剩余兜底文案会是英文

**负面 / 代价**

- **校验逻辑出现两份实现**，这是本决策的核心代价。用 `rulespec_test.go`
  把常量与窗口解析钉死，但 13 条判定的**组合逻辑**无法被机械证明逐位一致 ——
  残余漂移风险由「后端终审 + 显式漂移告警」承担，不假装消除了它
- 资产总量 +11%（202,972 → 约 225 KB），首屏解析增量估 1–3 ms
- `rule-fields.js`（181→约 250 行）与 `page-rules-form.js`（185→约 260 行）
  逼近单文件 300 行上限，后续再加字段需先拆分
- 三处硬门禁必须同步改：`adminui_test.go` 的白名单（`:32`）、
  index.html 双向引用（`:57`）、脚本加载顺序（`:87`）。漏改即 CI 红 ——
  这是刻意的，红总比运行时白屏好
- **界面不能显示实际时区偏移**：`TZ_OFFSET_SECONDS`
  （`internal/config/env.go:133`，默认 28800）未被任何 admin 端点暴露，
  前端无从获知。只能表达"按部署配置的业务时区自然对齐"这一语义。
  想显示真实数字需另开决策把它纳入 snapshot 或 policy。
  由此确立一条通用原则（由 designer 在
  `.workbuddy/artifacts/design-rule-viz.md §1.6` 提出，本 ADR 采纳）：
  **拿不到运行时真值的量，不展示推算值，改为展示该值的来源。**
  界面点名 `TZ_OFFSET_SECONDS` 这个变量名（编译期已知的常量，展示它不撒谎），
  而不是猜一个偏移数字。建议后续写入 DESIGN.md

**本决策查证中发现、但明确不在本轮修的两项后端缺陷**

两项均由 designer 的质疑触发查证，均不阻塞交付 —— 前端一律与 `Validate()`
当前行为对齐，界面承诺"提交不会被拒"而非"运行态最优"。

1. **burst 下限判据与实际填充速率不一致。** `rule.go:171` 用 int64 整除
   `Limit/winSec` 定下限，而 `TokenBucketRate()`（`:192`）用浮点，其唯一调用点
   `limiter.go:242` 将其作为 `Rate` 送进 Lua 桶。故 limit=10/window=3s/burst=3
   可通过门禁，但运行态是「桶容量 3、填充速率 3.33/s」——桶装不下一秒的填充量。
   **不改的理由**：`Validate()` 是加载期门禁，改成浮点会让今天能加载的配置
   明天加载失败（上例下限 3→3.33），存量部署升级即炸。用户的「无需兼容旧版本」
   限定在前端资产，不覆盖已部署的规则配置。若要修，方向是调整
   `TokenBucketRate()` 或桶容量语义，而非收紧门禁。
2. **`watermark > 100` 静默回落 80。** `<=0` 那半边**不可改** ——
   `Rule.Watermark` 是 `int` 无指针包装（对比 `Enabled *bool` 刻意用指针区分
   「显式 false」与「字段缺省」），故 YAML 省略该字段与显式写 0 解码后同为 0，
   该分支承担「缺省取默认」职责，改成报错等于要求所有存量配置显式填写。
   `>100` 那半边可安全改为报错，但需拆分单一条件并改动加载期行为，本轮不做。

**Out-of-scope**

不新增 spec 端点；不暴露 `TZ_OFFSET_SECONDS`；不改 `rule.go` 任何校验语义；
不做 JSON 语法高亮；不做 JSON 反向编辑（预览只读可复制）；
不做规则模板库；不引入任何前端框架、构建工具或 npm 依赖。
