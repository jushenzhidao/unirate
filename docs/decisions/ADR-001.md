# ADR-001: 限流准入热点路径改为零分配编码 + Key 前缀预计算

## Status

Accepted (2026-08-23) — 待后端实施

## Background

`internal/limiter/limiter.go:159-241` 的 `Check()` 在发起 Redis 调用之前，需要为每条规则做：
维度取值提取（`dimValues`）→ Key 字符串构造（`RateKey` / `ConcurrencyKey`）→
`luaRule` 切片组装 → `json.Marshal` 序列化。这段代码在**每个请求上都执行**，
规则数越多成本越高。

用 demo 生产配置（4 条规则：global 固定窗口 + biz.ip 固定窗口 + biz.token 滑动窗口 + biz 并发）
在 `golang:1.22-alpine` 容器内实测（arm64, GOMAXPROCS=4, benchtime=500000x）：

| 基准 | ns/op | B/op | allocs/op |
|---|---|---|---|
| 完整 PlanBuild（现状） | 1785 | 1144 | 27 |
| ├ `json.Marshal(lrules)` | 759.7 | 248 | 2 |
| ├ Key 构造（含 dimValues） | 755.9 | 480 | 22 |
| └ `dimValues` 单独 | 100.9 | 96 | 4 |

对照实验（同一基准框架内实现的候选方案）：

| 候选 | ns/op | B/op | allocs/op |
|---|---|---|---|
| 手写 `[]byte` 规则编码（复用 buffer） | 129.3 | 0 | 0 |
| 手写编码（每次新建 buffer） | 130.5 | 0 | 0 |
| Key 构造 + dims 前缀预计算 | 455.7 | 368 | 10 |
| Key 构造 + 前缀预计算 + `[]byte` 拼接 | 339.5 | 192 | 5 |
| **完整 PlanBuild（前缀预计算 + 手写编码）** | **798.6** | **408** | **13** |

关键观察：`json.Marshal` 占现状总成本的 43%，而 `luaRule` 的字段集是**完全固定**的
（8 个标量字段，无嵌套、无动态键），反射编码在这里付出的代价没有换来任何灵活性。
`strings.Join(dims, ".")` 每请求重算，而 `Rule.Dimensions` 在配置加载后即不可变。

## Decision

对 `Check()` 的 Redis 调用前路径做三项改造，**不触碰 Lua 脚本与两阶段求值语义**：

1. **手写 `luaRule` 编码器**，替换 `encoding/json`。输出必须与现有 `json.Marshal`
   **字节级兼容**（`omitempty` 语义一致：零值字段不输出），因为 `batch_check.lua`
   用 `cjson.decode` 解析，字段缺失与显式零值在 Lua 侧行为不同
   （`tonumber(nil)` vs `tonumber(0)`）。
2. **Key 前缀预计算**：在 `Rule.Validate()`（`rule.go:106`）中把
   `prefix + "|" + strings.Join(Dimensions, ".") + "|"` 缓存为 `Rule` 的私有字段
   （与既有 `winSec` / `natural` 缓存字段同一模式）。`RateKey` / `ConcurrencyKey` /
   `TokenBucketKey` / `TokenLedgerKey` 增加接受预计算前缀的变体。
3. **复用请求级缓冲**：`keys` / `lrules` / 编码 buffer 通过 `sync.Pool` 或挂在
   per-request 结构上复用，消除每请求的切片分配。

## Consequences

**正面**

- 单请求准入路径 CPU：1785ns → 798ns（**−55%**）；配合 ADR-002 可进一步降至约 475ns。
- 单请求分配：1144 B / 27 allocs → 408 B / 13 allocs（**−64% 字节，−52% 次数**）。
- 分配率下降直接降低 GC CPU 成本 —— 按 go.dev/doc/gc-guide 的摊销模型
  `GC CPU ∝ 分配率 × 每字节扫描成本`，736 B/req 的削减在 88k QPS 下等于
  少分配约 **64.8 MB/s**。

**负面 / 需明确认知**

- **这不是延迟优化，是 CPU 与 GC 压力优化。** 实测 Redis 往返在 256 并发下
  p50 = 2.4ms，1.3µs 的节省占端到端延迟不足 0.06%，**不会体现在 P99 上**。
  真实收益是单核可承载的 QPS 上限提高：1.3µs/req × 88k = 约 0.115 核/秒
  （≈ 11.5% 单核），在 5 核实例上约释放 2.3% 总 CPU。
  任何把本项宣传为「降低 P99」的说法都是错的。
- 手写编码器是**新的沉默逻辑错误高发点**：字段漏写、`omitempty` 语义偏差都不会
  编译报错，只会让 Lua 侧读到 `nil` 从而静默改变限流判定。
  强制配套防线见下。
- Key 前缀缓存引入「`Validate()` 未被调用则前缀为空」的隐式前置条件。
  `store.go:177` 与 `store.go:228` 两条加载路径都调用了 `Validate()`，
  但新增加载路径时若遗漏会产生错误 Key（**配额串号，等同安全缺陷**）。
  必须在构造 Key 的函数入口对空前缀 fail-fast，不得静默降级。

**强制配套验收**（缺一项即不合格）

- 差分测试：对全部规则类型 × 全部维度组合，断言手写编码输出与
  `json.Marshal` **逐字节相等**；覆盖所有 `omitempty` 字段的零值/非零值两态。
- 现有 `internal/limiter/limiter_test.go` 13 项须全绿且零跳过。
- `bash test/e2e/run.sh` 50/50 全通过，特别是 500 并发打 limit=50 必须仍恰好通过 50。
- 基准回归：`go test -bench` 数据写入 PR，实测 ns/op 与 allocs/op 达标才算完成。
