# ADR-002: 本地负缓存读路径增加原子空态短路

## Status

Accepted (2026-08-23) — 待后端实施

## Background

`internal/limiter/local.go:36-44` 的 `blocked()` 在每条规则上被调用一次
（`limiter.go:213`）。它对 `sync.RWMutex` 加读锁并查一次 map：

```go
l.mu.RLock()
until, ok := l.blocks[key]
l.mu.RUnlock()
```

问题在于**负缓存在绝大多数时间是空的** —— 只有短窗口规则超限时才写入
（`limiter.go:278-280`，且 `retry <= 10s` 才写）。稳态无超限流量下，
每请求要为「查一个必然为空的 map」付 N 次 RWMutex 读锁。

RWMutex 的读锁虽然不互斥，但仍有原子 RMW 操作，在多核高并发下
`readerCount` 这个共享 cacheline 会成为跨核争用点。

容器内实测（arm64, GOMAXPROCS=4, `RunParallel`, 4 个 Key/轮）：

| 场景 | ns/op | allocs/op |
|---|---|---|
| 空负缓存 + RWMutex（现状） | 343.5 | 0 |
| 非空负缓存 + RWMutex（现状） | 323.8 | 0 |
| 空负缓存 + atomic 计数短路 | **18.56** | 0 |

**18.5x 差距**。且空态与非空态耗时基本相同（343 vs 324ns），
证明成本几乎全部来自锁本身而非 map 查找。

## Decision

在 `localFallback` 上增加 `atomic.Int64` 条目计数，`blocked()` 入口先做无锁判断：

```go
func (l *localFallback) blocked(key string, now time.Time) (time.Time, bool) {
    if l.nBlocks.Load() == 0 {
        return time.Time{}, false   // 完全免锁
    }
    // 原有 RWMutex 路径不变
}
```

计数在 `block()` 写入与 `gcLocked()` 清理时同步维护。

**正确性论证（这是本 ADR 能否成立的唯一关键）：**

短路仅在计数为 0 时触发，即负缓存中确无任何条目，此时原路径
必然也返回 `(zero, false)`。因此短路与原路径**语义完全等价**，
不存在「本该拒绝却放行」的可能。

计数与 map 之间存在瞬时不一致窗口（计数已加、map 未写入，或反之），
但两个方向都安全：
- 计数偏大 → 多走一次加锁查询 → 结果正确，仅损失性能。
- 计数偏小（0 而 map 已有条目）→ 短路返回「未阻塞」→ 请求继续走 Redis 集中判定
  → **由 Redis 做权威判定，判定结果依然正确**。

负缓存本身只是「省一次 Redis 往返」的优化，从不是正确性来源
（`local.go:8-15` 已明确：它只会更严格，绝不放宽）。
短路最坏情况退化为「负缓存未命中」，等价于该优化不存在。
**因此本项不违反「不得以正确性换性能」的硬约束。**

## Consequences

**正面**

- 稳态（无超限）下每请求省 N 次 RWMutex 读锁。4 规则场景：
  343.5ns → 18.6ns，**每请求省约 325ns**。
- 消除一个跨核共享 cacheline 争用点，其收益随 GOMAXPROCS 增长而放大
  （本次测量在 4 核；核数更多时现状路径会更差）。
- 与 ADR-001 叠加后，准入路径 CPU 从 1785ns 降至约 475ns（**−73%**）。

**负面**

- 计数维护必须覆盖**所有**修改 `blocks` map 的位置。当前有两处
  （`block()` 与 `gcLocked()`），漏改会导致计数永久偏大 —— 后果仅是短路失效
  （退化为现状性能），不影响正确性。
- `quotas` map（降级路径 `allowQuota`）**不做同类优化**：它在 Redis 故障期间
  才被调用，属冷路径，且其正确性依赖精确计数，短路会引入真实风险。

**强制配套验收**

- 单元测试须覆盖：空态短路、写入后短路失效并正确拒绝、GC 清空后短路恢复。
- 并发测试：`-race` 下并发 `block()` / `blocked()` 无数据竞争。
- 现有 13 项限流测试与 e2e 50 项全绿。
