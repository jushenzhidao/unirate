# ADR-003: 将 TokenAdmit 与 Check 合并为单次 Redis 往返

## Status

**Accepted & Implemented (2026-08-23)** —— POC 达标，已落地并通过全部验收门禁。

POC 实测 **QPS +32.4% ~ +35.9%**（阈值 ≥20%），
p50 −22.7%~−27.3%，p99 −16.0%~−18.3%，
Redis CPU 全档 0.999 核（仍为瓶颈，归因成立）。

实现落点：
- `internal/limiter/scripts/batch_check.lua` 新增 `t='tkadmit'` 规则类型（Phase 1 只读，Phase 2 为 noop 占位）
- `internal/limiter/limiter.go` `Check()` 不再跳过 token 规则，改为编码为 `tkadmit`
- `internal/proxy/handler.go` 移除独立的 `TokenAdmit` 调用（方法本身保留，仍有测试覆盖）
- `internal/limiter/tkadmit_test.go` 新增 4 项定向测试

## Background

`internal/proxy/handler.go` 的准入流程当前是**两次串行 Redis 往返**：

```
:150  h.lim.TokenAdmit(...)   → tokenLedgerScript.Run(op='admit')   第 1 次往返
:156  h.lim.Check(...)        → batchCheckScript.Run(...)           第 2 次往返
```

更糟的是 `TokenAdmit`（`ledger.go:17-60`）对**每条** token 规则各发一次往返
（循环内 `Run`），规则数越多往返越多。demo 配置有 1 条 token 规则，
故当前是 2 次；若配置 3 条 token 预算规则则变成 4 次。

### 收益量化（已修正 —— 首版估算过高，此处为真实脚本实测）

**首版本 ADR 曾报「吞吐 +98%」，该数字来自简化探针脚本，已作废。**
团队复核指出 EVALSHA 单次成本口径不一致（18.78µs vs 累积 3.56µs），
经重测确认：**首版用的是简化脚本（3.70µs/call），真实 `batch_check.lua`
是 22.3µs/call —— 贵 6 倍**。用简化脚本推导出的往返收益被系统性高估。

用**真实 `batch_check.lua` + 真实 `token_ledger.lua`** 重测
（`CONFIG RESETSTAT` 后受控负载、400 次预热、5s 采样、同步采集双侧 CPU）：

| 并发 | 方案 | QPS | p50 | p99 | Redis 核数 | 客户端核数 |
|---|---|---|---|---|---|---|
| 256 | 现状 2 往返 | 21,848 | 11.26ms | 22.19ms | 0.997 | 0.871 |
| 256 | 合并 1 往返 | **28,004** | 8.52ms | 18.01ms | 0.995 | 0.605 |
| 256 | 参照 纯 check | 30,217 | 8.16ms | 16.15ms | 0.999 | 0.612 |
| 512 | 现状 2 往返 | 22,438 | 22.39ms | 31.02ms | 0.999 | 0.918 |
| 512 | 合并 1 往返 | **29,266** | 16.86ms | 26.08ms | 0.999 | 0.631 |
| 512 | 参照 纯 check | 30,558 | 16.17ms | 24.58ms | 0.999 | 0.653 |

**修正后的真实收益：QPS +28.2% ~ +30.4%，p99 −15.9% ~ −18.8%。**
不是 +98%。

为何不是翻倍：`token_ledger.lua` 的 `admit` 分支只有 `GET` + `PTTL`
（12.6µs/call），远比 `batch_check`（22.3µs/call）便宜。
两者成本不对等，因此消除它不会让吞吐翻倍。
「参照 纯 check」一行给出了理论上界（30.2k / 30.6k）——
合并后达到 28.0k / 29.3k，**已取得该上界的 93~96%**，
剩余差距就是新增 `GET`+`PTTL` 的固有成本，无法再压缩。

**归因已证实（关键）**：三组测量中 Redis CPU 恒为 **0.995~0.999 核，
即 100% 跑满单核**，而客户端仅占 0.61~0.92 核。
**瓶颈确凿在 Redis 单线程，不在客户端，也不在 gateway。**
因此「减少往返数」的收益方向成立，只是量级需按上表修正。

## Decision

把 Token 预算准入合并进 `batch_check.lua` 的 Phase 1，作为一种新规则类型
（例如 `t = 'tkadmit'`），**严格遵循既有两阶段语义**：

- **Phase 1（只读试算）**：`GET` 账本 Key，`used >= limit` 则返回拒绝。
  与现有 `token_ledger.lua` 的 `admit` 分支（`token_ledger.lua:29-37`）逻辑等价。
- **Phase 2（提交）**：token 准入**不写入任何内容** —— Token 是事后计量，
  准入期只读余额，这与 `ledger.go:8-16` 已定案的语义一致。

因此该规则类型在 Phase 2 中是 no-op，天然不破坏
「全通过才提交」的不变量，也不引入新的中间态。

`TokenReserve` / `TokenSettle` 保持独立不动 —— 它们在响应结束后异步执行
（`handler.go:336`、`handler.go:387`），不在请求准入关键路径上。

## Consequences

**正面**

- 准入路径 Redis 往返：2 → 1。真实脚本实测吞吐 22.4k → 29.3k QPS
  （512 并发，**+30.4%**），p99 从 31.0ms 降至 26.1ms（**−15.9%**）。
  已达「纯 check」理论上界的 96%。
- 多条 token 规则场景收益更大：N+1 次往返压缩为 1 次，
  与 Advisory-4 对 `Check()` 所做的优化思路完全一致。
- Redis 侧 CPU 与连接占用同步减半，间接抬高整个网关集群的容量天花板。

**负面 / 风险**

- **这是本轮唯一触碰 `batch_check.lua` 的改动**，而该脚本是项目最核心资产
  （同时保障 P0-1 配额放大与 P0-5 计数器污染两项修复）。
  风险实质：改错会同时破坏两项 P0 保障，且可能表现为**沉默逻辑错误**
  —— 脚本仍返回结果、请求仍被处理，只是判定错了。
- 需在 Go 侧改动 `Check()` 的规则组装逻辑，把 token 规则从
  「跳过」（`limiter.go:175-177` 当前显式 `continue`）改为「以 tkadmit 类型纳入」，
  同时确保 `TokenReserve`/`Settle` 的规则筛选不受影响。
- 拒绝时的 `RetryAfter` 语义需保持一致：现状用 `PTTL`（`ledger.go:49-52`），
  合并后需在 Lua 内取同样的 `PTTL` 并放入返回值第 3 位。

**为何仍标记为「需 POC 验证」**

上表虽已用真实 `batch_check.lua` 实测，但合并形态是**模拟**的：
在脚本头部插入 `GET` + `PTTL` 两条只读命令，
而非完整实现「token 规则作为 `t='tkadmit'` 类型纳入规则数组」。
真实实现还需承担 cjson 解码多一个规则对象的成本，
以及 Go 侧规则组装逻辑的改动。故实测值是**乐观上界**。

**POC 验收阈值（已按修正后基线重定）：**

1. **吞吐提升 ≥ 20%**（而非首版的 50%）。
   依据：真实脚本实测为 +28.2%~+30.4%，理论上界（纯 check）为 +38%；
   扣除完整实现的额外 cjson 成本后，20% 是合理的保底线。
   **低于 20% 说明实现引入了预期外开销，应查明原因而非直接放弃；
   低于 10% 则该项不值得其触碰核心脚本的风险，回退。**
2. Redis CPU 须仍为瓶颈（跑满单核）。若合并后 Redis CPU 未跑满而 QPS 未提升，
   说明瓶颈已转移，需重新归因。
3. 500 并发打 limit=50 仍**零误差**恰好通过 50 个。
4. Token 预算耗尽时的拒绝行为与 `RetryAfter` 与现状逐位一致。
5. `cjson.decode` 在规则数增加后的成本曲线（是否成为新瓶颈）。

**强制配套验收**

- 新增 Lua 层单元测试：token 准入通过/拒绝、与其他规则类型混合、
  以及「token 规则拒绝时其他规则计数器不得变化」（两阶段不变量）。
- e2e 50/50 全绿，尤其 Token 预算相关断言（`run.sh:243-254`）。
- 前后对比压测数据入 PR，含**双侧 CPU 采集**（Redis 与压测客户端），
  未达到 ≥ 20% 吞吐提升需查明原因，< 10% 则回退该项。

## 实施后实测（POC 结论）

用**真实 `batch_check.lua`**（含新增 tkadmit 分支）交替 3 轮取中位数，
before = 独立 `token_ledger admit` + `batch_check` 两次往返，
after = 单次 `batch_check`（token 规则作为 KEYS[5] 的 tkadmit）：

| 并发 | before QPS | after QPS | QPS 变化 | p50 变化 | p99 变化 | Redis 核数 |
|---|---|---|---|---|---|---|
| 128 | 23,754 | 32,287 | **+35.9%** | −27.3% | −18.3% | 0.999 |
| 256 | 22,839 | 30,448 | **+33.3%** | −22.7% | −16.0% | 0.999 |
| 512 | 22,740 | 30,112 | **+32.4%** | −24.1% | −16.2% | 0.999 |

单次脚本成本从 12.4µs 升至 22.3µs（多做一次 GET+PTTL 并多解一个规则对象），
但往返数减半，净收益为正 —— 与 ADR-004 的容量公式
`上限 ≈ 1e6 ÷ 脚本µs ÷ 往返数` 吻合（22.3µs 单往返 ≈ 31k，实测 30.1-32.3k）。

**归因**：Redis CPU 在全部并发档恒为 0.999 核（100% 跑满单核），
瓶颈仍在 Redis 单线程，收益归因成立。

## 实施中发现的高危陷阱（已防住并加回归测试）

`batch_check.lua` 的 Phase 2 用 `ipairs(plans)` 遍历，
而 **`ipairs` 遇到第一个 nil 即停止**。
tkadmit 是「只读不写」的规则，若它不在 `plans` 中占位就会留下空洞，
导致**其后所有规则的提交被静默跳过** —— 判定通过但配额没扣，
即 **P0-1 配额放大的复现**，且不报错、不崩溃、不影响任何既有测试。

这是典型的沉默逻辑错误。防线：
1. tkadmit 与未知类型均写入 `plans[i] = { t = 'noop' }` 占位；
2. `TestTkAdmitDoesNotBreakLaterRuleCommit` 刻意把 token 规则排在
   fixed 规则**之前**，若占位被误删即失败；
3. **变异验证已执行**：手动移除占位后该测试确实变红
   （放行 10 个而非 3 个），证明它不是摆设。
