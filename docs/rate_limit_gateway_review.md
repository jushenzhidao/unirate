# unirate 频控网关 Spec 架构评审报告

> 评审对象：`docs/rate_limit_gateway_spec.md`（通用频控代理网关 v1.0.0-alpha.1）
> 评审人：首席架构师 高见远 | 门禁核验：项目总监 大湾区靓仔
> 评审日期：2026-08-23
> 评审结论：**FAIL** —— 存在多处"照着开发必然出错"的架构级矛盾与安全裸奔面，须修正后出 v1.0.0-alpha.2 复审

---

## 总体评价

Spec 结构清晰，分层限流思路（L0~L4）、存储分层、防泄漏兜底意识都不错。但存在三类硬伤：

1. **分布式语义自相矛盾**（本地令牌桶 vs 无状态多实例）
2. **Lua 脚本边界 bug**（超限不回滚 → 计数器污染）
3. **安全管理面完全缺失**（admin 接口零鉴权，且是切流入口）

---

## BLOCKING（必须修正，按严重度排序）

### P0-1【架构矛盾】L1/L2 "本地内存令牌桶"在多实例下集群语义不成立

- **证据**：§2.3.6 存储分层表写 "L1/L2：本地内存 + Redis 兜底"；§3.2 数据流 [4] 中 `global:1m:Token` 用"本地令牌桶（预检）"；但 §3.1/§3.5 明确"无状态设计，多实例部署"，且 L1 定义是"保护网关集群"、L2 是"保护下游服务总量"（§2.3.5）。
- **问题**：N 个实例各持独立令牌桶 → 实际配额 = limit × N，"保护下游总量"完全落空。"本地内存 + Redis 兜底"语义未定义（每次双写？周期同步？），开发者只能猜。
- **修正方向**：二选一并写死：
  - (a) L1/L2 需要集群语义 → 复用 Redis Lua 集中计数，本地仅做只读预检缓存（可少量超卖但绝不能每实例一个桶）；
  - (b) 引入分布式令牌桶（GCRA / 每实例分片配额 + 周期性再平衡）。
  - 同时在 §2.3.6 表中删除"Redis 兜底"这种含糊表述，写明数据流。

### P0-2【逻辑矛盾】令牌桶适用范围与 Key 设计互相打架

- **证据**：§2.3.4 说令牌桶适用"短窗口（≤1s）"；但 §3.2 数据流规则4 和 §6.3.1 规则 id:12 都是 `window: 1m + token_bucket`。更根本的：令牌桶是**持久状态桶**（rate+burst，无窗口重置概念），而 §6.4.1 的 Key 规范 `ratelimit:{dims}:{vals}:{window}:{window_boundary}` 给每个窗口边界生成新 Key——带 boundary 的令牌桶每分钟重建，退化为"固定窗口+突发额度"。
- **修正方向**：定义 token_bucket 专属 Key（不含 boundary，如 `ratelimit:tb:{dims}:{vals}`）和 Hash+Lua 持久桶脚本（rate/burst/last_refill 三字段）；或规定 metric=token 的长窗口规则一律用固定/滑动窗口，令牌桶限制在 request 短突发场景。二者择一，消除 §2.3.4 与数据流的矛盾。

### P0-3【安全隐患】admin 管理接口零鉴权——切流入口暴露

- **证据**：§6.2 五个 /admin 接口（含 `PUT /admin/biz/{biz}/upstream` 可把任意 biz 流量指向任意主机）无任何鉴权、授权、审计、网络隔离方案。§2.7 对 `X-Upstream-Base-URL` 的 SSRF 防护仅一句"忽略或返回 400"，"合法"未定义（scheme 白名单？内网 CIDR 黑名单？DNS rebinding？）。
- **修正方向**：admin 必须补齐——独立监听端口（仅内网可达）+ 鉴权方案（MVP 用静态 Bearer Token 或 mTLS 二选一，写进 Spec）+ 变更审计日志。X-Upstream-Base-URL：生产默认关闭 + 上游域名 allowlist，并定义校验规则（仅 http/https、禁环回与内网网段、禁重定向跟随）。

### P0-4【设计缺陷】并发控制 INCR/DECR 生命周期有 3 个洞

- **证据**：§2.5.2 "INCR 后 > max_concurrent → 拒绝 429"——被拒请求**没有 DECR**，拒绝流量每次 +1 永久占用额度，攻击者可用被拒请求打满并发额度（泄漏速率=拒绝 QPS，远快于 TTL 30s 自愈）。§3.2 数据流中并发 INCR 是第一道检查，但后续规则 2/3/4 任一触发拒绝时也**没有回滚已 INCR 的并发计数**（数据流只写成功路径 [7] 的 DECR——happy-path bias）。TTL 兜底自身有洞：30s TTL 过期后 key 消失，旧请求完成时 DECR 会**误减新窗口的计数**（甚至减成负数，导致限流失效）。
- **修正方向**：
  1. 拒绝路径一律"INCR 后判断超限则立即 DECR"，写成 Lua 原子脚本；
  2. 多规则检查的补偿顺序写进数据流（任一规则拒绝 → 回滚已通过的并发/计数）；
  3. 放弃"key 级 TTL"方案，改为"每请求携带 deadline 写入 ZSet/Hash + 后台清扫过期成员"或"DECR 后值 <0 时归零并告警"；
  4. §3.4.1 与 §6.4.2 的并发 Key 格式互相不一致（前者示例缺 dimension value），一并统一。

### P0-5【Lua 正确性】固定窗口/Token 扣减脚本"超限不回滚"导致计数器污染

- **证据**：§3.4.2 固定窗口脚本 INCR 后 `current > limit` 直接 return 0，不 DECR——被拒请求永久占用窗口计数。后果：①攻击者用被拒请求打满窗口（DoS 放大）；②水位监控（§2.6.2 声称"精确"）读到的 used 虚高，误触发告警甚至自动收紧。§3.4.4 Token 扣减脚本同样不回滚，且语义混乱：Token 是响应后计量，"扣减后超限 return 0"意味着拒绝一个已完成的请求？未定义。§3.4.3 滑动窗口脚本的 ARGV[4]（member 唯一后缀）来源未定义——同秒+同值会 ZADD 覆盖漏计。
- **修正方向**：两个脚本改为超限时回滚（`DECR`/`INCRBY -tokens`）再 return 0；Token 脚本的调用时点（预检预扣 vs 事后核销）和 return 0 的处置语义写清楚；滑动窗口 member 明确为"网关生成的全局唯一请求 ID"。

### P0-6【计量一致性】×1.2 缓冲只扣不退，Token 计量系统性虚高 20%+

- **证据**：§2.4.4 "估算值 × 1.2 后扣减" + "检测到 usage → 精确值覆盖估算值"。"覆盖"的补偿算法没定义：精确值 847 < 估算扣减 1016 时，多扣的 169 退不退？不退则全局 Token 预算被提前 20% 耗尽。"本地累加、SSE 结束一次性刷 Redis"（§2.4.5 accumulate_local）意味着长 SSE 期间已消耗 Token 对其他实例不可见——超卖窗口 = SSE 时长。§3.2 数据流 [4] 的"global:1m:Token 预检"预检值从哪来也未定义。
- **修正方向**：明确账本模型：预扣（估算×1.2）→ 结束核销（精确值）→ 差额 INCRBY 负值退回，写成一条原子脚本；本地累加刷盘间隔加上限（每 1s 或每 N chunk 增量刷一次）压缩超卖窗口；预检语义写明（基于历史均值预估）或删掉预检。

### P0-7【架构矛盾】配置中心 Source of Truth 三个候选并存

- **证据**：§2.2 P1 写"Redis / MySQL 配置面板"；§3.3.6 写"定时从 Redis/MySQL 拉取"；§7.1 选型又推荐"etcd + viper"。三套系统谁是权威、谁是缓存没有定论。管理后台（独立 Python 服务）写哪、网关读哪，链路缺失。MySQL 表与 Redis Hash 的双写一致性、失效广播机制全文未提。
- **修正方向**：定一个 SoT。建议：MySQL 持久层（管理后台唯一写入口）→ 写后发布变更（Redis Pub/Sub 或版本号轮询）→ Redis 为网关读取层 → 删除 etcd（该场景多余组件，viper 仅作本地文件配置加载器保留）。写路径、失效路径、回滚路径画进 §3.3.6。

### P1-8【Key 设计缺陷】分隔符冲突 + 窗口边界格式不统一 + 时区语义未定

- **证据**：§6.4.1 维度值用 `_` 连接，而 path 本身含 `/` 和 `_`（biz 校验 §2.1 也允许 `_`）：`ratelimit:biz_path_token:order_/v1/create_a3f9b2c1` 无法反解析，且不同维度组合可碰撞出同 Key。窗口边界：§3.4.1 用 datetime 格式（20250823010000），§6.4.3 用 epoch 秒——同一规范两种格式。d/w 窗口用 UTC epoch 对齐 → 国内业务 1d 窗口在早 8 点重置，未声明时区策略。
- **修正方向**：维度值统一安全编码（path 段取 SHA256 或 URL-encode，biz 规则改为不允许 `_`）；分隔符改用编码后值中不会出现的字符；窗口边界统一为 epoch 秒；明确 d/w 边界时区（UTC 写入运维文档，或可配置业务时区）。

### P1-9【无法实现】维度提取规则缺失：token 从哪个 header 取、IP 如何防伪造

- **证据**：§2.3.2 token 维度只说"从请求头提取"——Authorization Bearer？X-Api-Key？多 header 优先级？ip 维度示例直接信任 `X-Forwarded-For`（§3.2 步骤1）。XFF 客户端可伪造，攻击者每请求随机 XFF 即绕过 ip 限流。
- **修正方向**：定义可信代理链模型：`trusted_proxy_hops: N`，从 XFF 右数第 N 位取真实 IP，无 XFF 时取 RemoteAddr；token 提取配置化（header 名列表 + Bearer 前缀剥离规则）写进 §2.3.2。

### P1-10【策略缺陷】Fail-Open 一刀切，对 Token 预算类场景等于烧钱开关

- **证据**：§3.5 "Redis 故障 → L3/L4 Fail-Open"。L4 承载 metric=token 的预算控制——Redis 挂掉期间所有 Token 预算失效，事后计量也无法落账。
- **修正方向**：按 metric 分治：metric=request → Fail-Open 可接受；metric=token → Fail-Close 或"本地保守配额降级"（每实例兜底配额 = 总量/N）。补 Redis 恢复后的对账策略（断连期间本地记账回补）。

### P1-11【验收缺失】无 SLO/性能验收标准、无 liveness/readiness 区分、无端到端验证步骤

- **证据**：§6.1.2 单一 /health 返回 healthy，Redis 挂了依然 healthy → SLB 继续导流。§7.2 有"P99<5ms"断言但无验收口径。全文没有可执行的端到端验证步骤——按 spec-as-contract 标准，"规格停在实现完成"即不合格。
- **修正方向**：拆分 /live（进程活着）与 /ready（Redis 可达 + 配置已加载 + L0 未触发）；定义 SLO 表（透传额外延迟 P99 目标、SSE 首字节延迟、单请求规则检查 RTT 上限）；补端到端验收步骤（核心成功流 + 429 流 + Redis 故障流 + SSE 计量流）。

## 修正优先级建议

1. **最急**：P0-3（安全暴露面）+ P0-4/P0-5（计数器正确性，照抄即坏）
2. **动工前必须定案**：P0-1/P0-2（分布式限流语义，决定核心架构返工量）
3. **随后**：P0-6/P0-7，再 P1-8/P1-9（否则无法实现）
4. 全部 P0 + P1-8/P1-9 完成后，出 **v1.0.0-alpha.2** 复审一轮
